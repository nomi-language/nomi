# Nomi Roadmap: Big-Ticket Items

The strategic punch list of large, cross-cutting initiatives: the things that
take a design pass and several changes. It complements:

- [`spec.md`](spec.md), the canonical spec for what the language does.
- [`feature-status.md`](feature-status.md), the aspirational-spec punch list, gaps in shipped features, tooling capabilities and known defects.

This file is the forward view: open work only. When an item lands, delete it here; the spec says what works, and feature-status.md lists what the item left unbuilt.

## The organizing principle

Sort by retrofit cost: how expensive a thing is to change after code depends
on it.

1. **There is one engine.** The front end (parse, analyze, type-check) feeds
   `internal/irbuild`, which lowers every body to IR; the VM compiles that IR to
   bytecode and runs it over `rt`'s values. `nomi run`, `nomi test`, the REPL,
   the tour, `nomi build`'s executables and Go embedders all use it. Golden
   files under `testdata/expectations/` are the only oracle.
2. **Irreversible semantics before additive features.** A numeric, string or
   collection decision baked into every program matters more than any feature
   that can be added later without breaking anyone.

## Track 1: Execution and tooling

- [ ] **Stdlib startup cost.** A built `nomi` runs hello world with no program record in about 44 ms on an Apple M2 Max, from 119 ms: the stdlib is built from its modules' interfaces with no body checked, and only the modules a program reaches (the prelude, std/assertions and std/io with what they import, 47 of 101 modules, then each module a build reaches with its imports), the IR builder restores only those from the std bundle, and a machine decodes its CLDR data only when a frame reads it. The std setup takes about 18 ms of it (the base modules' build 10 ms, their facts 1-3 ms, the `StdBase` 3 ms, the artifact read 2 ms), the bundle 5 ms. The target was under 10 ms. Next: interfaces decoded straight into symbols and types instead of registered through the sweeps, which is most of the base build and of its 11 MB of fresh memory; a build of further modules costs about 3 ms over those already built, for the program-wide indexes it folds over them, which could be laid over the smaller stdlib's base instead; and the listed modules' kept lowering is decoded whole, so a program reaching one listed module builds all of them (the HTTP chapter's first block builds 96 modules).
- [ ] **Incremental compilation, what remains.** The language server checks incrementally in memory (`internal/analysis/recheck.go`, `recheck_dependents.go`), opens a project from a record of its files' interfaces, facts, references and the entry's kept lowering (`stored_program.go`), and takes edits in a program opened so (`stored_edit.go`, `stored_inplace.go`, `stored_lowering.go`, `stored_refs.go`); `nomi run`, `check`, `test` and `build` relink a kept program from its file records (`vmhost/filerecord.go`). At 50k generated lines (221 files) the first body edit after an open from a record takes 8 to 34 ms, references to a function 137 files call 0.12 s, and the entry's lowering after a body edit 0.28 s. What remains. A program with Go bindings keeps no record: the server builds each of its documents on its own and keeps no program for it, so moving such projects onto kept programs comes first. An edit that leaves something to report is taken from the record unless it is a diagnostic only the program checked whole words (an impl collision or orphan, a missing impl, a reduction's diagnostic in a file the edit does not check again), or the program has an application type. In a program with an application type, an edit that changes the walk its application-field roots take of a checked file's bodies (a new call, a read added or moved into a lambda) checks the whole program: the walk follows calls into other files' bodies (`appReadWalker.contained`, interface default methods, every impl of a dispatched method), and its alias and inspection state carry from one file's body into the next, so per-file facts would have to hold each executing expression with its resolved reference and replay the walker over them; the server compares each checked file's walk summary instead (`AppWalkSummary`), which a positions-only edit keeps. `nomi check`'s relink from file records compares the same summaries. The language server checks an edit that reaches more than 16 files and a quarter of the program (a hub's signature) whole, and that stays: at 50k lines the hub's signature reaches 210 of 221 files, each of whose checks against interfaces builds the hub's interface and its own closure (opening a leaf from a record costs about 10 ms, so 2.1 s for 210), and each file's lowering links against every other's, where the whole check takes 1.03 s.
- [ ] **Debugger follow-ups.** The debugger plan has landed (feature-status's *Debugger* section). Left: attaching to a running process or a `nomi build` executable (the image keeps the debug info); debugging a program with Go bindings, which runs in a generated wrapper process; and step back in a program with more than one task, which a replay cannot reproduce without recording the scheduler's choices too.
- [ ] **Programs the builder declines.** The checker accepts some programs the IR builder cannot lower, and `nomi run` refuses them before running with a "not supported yet" error at the code the builder stopped at. Every recorded program runs, so each remaining shape is a gap an ordinary program can hit. The known shapes are listed under feature-status's known defects.
- [ ] **The builder's `mobile` flag.** The builder's `lower` still returns whether a value may be read more than once without a copy, and about a hundred call sites pass it on. The VM evaluates each temporary once, so the flag and the `irCopyForce` copies it guards could go. It is a large mechanical change with no behaviour behind it.
- [ ] **FFI follow-ups.**
  - Runtime-typed dispatch (an `import_impls` escape hatch) for values from FFI or deserialization whose impls the analyzer cannot record statically.
  - `host type` field access and Nomi-side construction.
- [ ] **A prebuilt `nomi` still needs Go for Go FFI beyond lib/.** A release runs, tests and builds a project whose bindings are all the first-party lib/ modules' at its commit on prebuilt binaries from a lib archive (`internal/ffirun/libprebuilt.go`). Any other Go binding, a lib/ module at another commit, a `wasip1/wasm` build of a lib/ project and a program importing `std::compiler` still build a wrapper or a nomi-vm with Go; without Go they refuse naming what needs it. No release has been cut with the lib archives yet, so the download path is tested only against a local server. Homebrew and Scoop packages are not written: they need a tap and a bucket repository.
- [ ] **Standalone WASM programs, what remains.** `nomi build --target js/wasm` and `--target wasip1/wasm` write valid modules, and the wasip1 ones need no file access. A hello world is 11 MB (2.0 MB brotli) and starts in about 130 ms under Node, most of it compiling the module. Browser use is checked by hand in Chromium only: `nomi build --web` pages, a cached wasip1 `nomi-vm` running `.nomic` programs framed on stdin through `@bjorn3/browser_wasi_shim`, and `nomi-wasi.js` loading and running programs in the reactor. The automated tests drive all of these under Node; Firefox and Safari are untried. wasmtime has run a command module; the reactor has not been tried there. GC behaviour is unmeasured. `--web` links a project's Go bindings into `app.wasm` (tested under Node; a bound package that does not build for js/wasm is refused at its `gopkg`), refuses file access where a `files` option served from the worker's `fs` could stand in, and has no `nomi test` counterpart.
- [ ] **Link only the Go code a program reaches, beyond the network.** `nomi build` appends a program that reaches no network crossing to a runner built without net/http, crypto/tls and net (`nomi-vm-nonet`, about a third smaller). The rest of std's Go side (CLDR formatting, collation, regex, processes) is still linked into every runner; linking each program's runner from the crossings it reaches, as Go-FFI projects' runners are, would cut every target further. A browser client that calls `fetch` through `syscall/js` without `http.Client` would cut a program that does use std::http by about 4.5 MB.
- [ ] **Calling JavaScript from Nomi.** A page calls a Nomi program's exported functions (`nomi.js`'s `load` and `call`), but Nomi cannot call the page: no DOM, `fetch` or local storage. The mirror of `export fn` would be a small set of host functions in a `std::web`-like module, or the page passing callbacks to `load`. Nothing is designed.
- [ ] **An npm package for the wasm build** (`cmd/nomi-wasm`, the tour's runtime) with a small JS API: run source, hover, semantic tokens.
- [ ] **Tour hardening, what remains.** The stack-depth limit (`rt/calldepth_js.go`, 1,000 calls) and the run-worker's recovery were measured in Chrome and Node only; Firefox and Safari are unmeasured. And a Go fatal error prints a goroutine trace to the worker's console naming the build machine's paths; `-trimpath` would remove them, and it must go on both `scripts/build-tour-wasm.sh` and `vmhost/tour_bundle_test.go`'s rebuild at once.
- [ ] **Doc-gen, registry and package-manager UX.** `nomi doc`, publishing, distribution polish. Nomi modules ride the Go module proxy.
  - `nomi publish` is reserved. Publishing a module is pushing a version tag to its repository, as for any Go module, and the module proxy serves it from there.
  - A registry. There is no Nomi-specific registry, and none is planned; if Nomi-specific module discovery becomes a need, the simplest path is metadata indexing on top of existing Go module hosting rather than a parallel registry.
  - Compiler-enforced semver: a compiler that diffs the public API between versions and rejects mismatched version bumps. A long-horizon nice-to-have. The closest existing precedent is Elm/Gleam; the mechanism requires both a registry hook (where to compare against) and a published-API extraction step that doesn't exist yet.

## Track 2: Irreversible semantics

- [ ] **Language versioning and compatibility.** The mechanism (editions, fixers, a compatibility promise) for when the language stops breaking. Until then it breaks freely, which is correct before a first release.
- [ ] **Exhaustive struct pattern opt-in.** Struct pattern matching is partial by default: unmentioned fields are ignored. A `!..` marker could opt into exhaustive field matching, so `User{name, age, email, !..}` would become a compile error when `User` gains a field. This is the inverse of Rust, where `..` opts *out* of exhaustive matching. It waits on real usage showing the need.

## Track 3: Architecture to leave room for

- [ ] **A stable serialization format.** The linked-IR image (`ir.EncodeImage`/`DecodeImage`) is the one serialized form today and carries no compatibility promise outside `.nomic`, which `ir.FormatVersion` versions. An object is the same format: one module encoded alone, whose symbols carry their linkage names, so objects, instances and images share one codec and one version. Front-end artifacts have a codec of their own beside it: a file's interface (`analysis.FileInterface`) writes its declarations' nodes with `internal/ast/astcodec`, generated from the AST's types, under its own version.
- [ ] **WASM Component Model interop** for cross-language imports and exports. WIT interfaces and `wasip2` components are the standard that would replace the wasip1 reactor's generic `nomi_call` ABI, which passes function names and JSON as data because one prebuilt runner serves every program and Go fixes a module's export names when it links it. Go cannot produce components yet. Track it; nothing is designed.

## Track 4: Big but additive

- [ ] **Unified container type/value syntax.** Tuples (`#(Int, String)` ↔ `#(1, "x")`) and anonymous structs (`#{a: Int}` ↔ `#{a: 1}`) already use one outer syntax for type and value; lists and maps do not (`List<Int>` vs `[1, 2, 3]`). Proposal: also accept `[Int]` and `%{String => Int}` as type forms. Needs its own design.
- [ ] **Field-projection derive** (`derive Getters for T`). For an interface whose functions are pure field projections (`fn hour(value: self) -> Int`), synthesize the trivial impl, which would remove boilerplate like `std::calendar`'s `DateParts`/`TimeParts` impls. `derive` covers `Equatable`, `Hashable`, `Comparable`, `Debug`, `Display`, `ToJson` and `FromJson` today.
- [ ] **Opaque handles for exported functions.** Every argument and result of an `export fn` crosses as JSON, so a value the host passes back unchanged is encoded and decoded on each call. A handle (a value that stays in the VM, referred to by an id) would matter for large values and values with no JSON form. Wait for a program that needs it.
- [ ] **Checked examples in stdlib `///` comments.** The generated reference renders a declaration's `//!` attached tests as runnable editors, and those are the stdlib's examples. A ` ```nomi ` block inside a `///` comment is only highlighted: nothing parses, checks or runs it, so one can go stale unnoticed. Either check those blocks or settle that `//!` is the only example form.

## Track 5: Standard library I/O and services

Where each item lives follows one rule. std holds what Go's standard library can back with no third-party code: `std/fs`, `std/sql`'s vocabulary, later `std/http` over `net/http`. `lib/` holds first-party modules that need third-party Go code or are opinionated layers over std: database drivers (`lib/sql/sqlite`), `lib/sql/sqlkit`, later an HTTP router or framework. Each `lib/` module is its own module with its own `go.mod`, versioned with nomi's commits, tested by nomi's checks, and added by users with `nomi add github.com/nomi-language/nomi/lib/...`.

What a program needs to talk to the world outside the VM. The items are in the agreed order. Items 1 and 2 and the subprocesses `std::process` now has share one stream type (`Reader`/`Writer`) and one test seam, and were designed together in the I/O design proposal (`docs/design/io.md`, not committed), which also sketches 3, 4, 5 and 7. Every item is backed by Go's standard library, so no program needs a Go toolchain to use it.

- [ ] **2. The file system, the rest.** `std::fs`, `std::path` and `std::fs_testing` exist (whole files with a `WriteMode`, lines and chunks, streams, directories, walks and globs, metadata, symlinks and modes, `io.File` with reads and writes at a position, `fs.within` over `os.Root`, temporary directories, an in-memory sandbox, a conformance suite, the browser's in-memory file system). Missing: a test group line that seals a test's real file calls. Paths use `/` on every system, Windows hosts accepting `\` too.
- [ ] **5. HTTP under Node.** `std::http`, `std::tls` and `std::net` cover Go's HTTP packages (docs/design/http.md; `internal/stdhttp/inventory.txt` names each of Go's identifiers and what Nomi does with it). Missing: a js/wasm request run under Node, where Go's transport does not use `fetch`.
