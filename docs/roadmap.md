# Nomi Roadmap: Big-Ticket Items

The strategic punch list of large, cross-cutting initiatives: the things that
take a design pass and several changes. It complements:

- [`spec.md`](spec.md), the canonical spec for what the language does.
- [`feature-status.md`](feature-status.md), what works today: shipped compiler and tooling milestones, the aspirational-spec punch list and known defects.

This file is the forward view: open work only. When an item lands, delete it here and record the result in feature-status.md.

## The organizing principle

Sort by retrofit cost: how expensive a thing is to change after code depends
on it.

1. **There is one engine.** The front end (parse, analyze, type-check) feeds
   `internal/irbuild`, which lowers every body to IR; the VM compiles that IR to
   bytecode and runs it over `rt`'s values. `nomi run`, `nomi test`, the REPL,
   the tour, `nomi build`'s executables and Go embedders all use it. Golden
   files under `testdata/expectations/` are the only oracle.
2. **Irreversible semantics before additive features.** A numeric, string or
   collection decision baked into every program matters more than any feature
   that can be added later without breaking anyone.

## Track 1: Execution and tooling

- [ ] **Stdlib startup cost.** A built `nomi` runs hello world in about 100 ms on an Apple-silicon Mac: about 65 ms analyzing the stdlib, about 28 ms lowering it, and a few ms on the program. Serializing the full analysis is not worth it: it points into the AST throughout (node-keyed type maps, `Symbol.Node`, cyclic type graphs, lazy registrations holding closures), so a codec would run to thousands of lines and decoding would still rebuild about 15 MB of objects. What should be serialized is each file's interface (its exported names, signatures, types and impls), as Go's export data and Rust's `.rmeta` do; once incremental compilation (below) defines that interface, the stdlib's can be written at build time. Until then, two cheaper levers remain. A generated `ast.Children` in place of the reflective walk measured about 10 ms less. Analyzing only a program's stdlib import closure would cut analysis from 66 to about 39 ms for hello world (the prelude's closure is 37 of 50 modules) and shrink lowering with it, but diagnostics that read every stdlib module (import suggestions, derive scopes) would need care.
- [ ] **Incremental compilation, what remains.** The language server checks incrementally in memory: an edit inside a body rebuilds only that file's bodies, a signature edit checks the edited file and the files that import it, and every other file's analysis is kept (`internal/analysis/recheck.go`, `recheck_dependents.go`). At 50k generated lines (`internal/scalebench`) a body edit takes 5-9 ms and a signature edit in a leaf 85 ms; one that every file depends on, or one that changes impls, still checks the whole program (about 650 ms). Three parts remain. Lowering: the server lowers the whole program 400 ms after each burst of typing to report bodies a run would refuse (747 ms at 50k lines). Lowered functions cannot be reused across lowerings, because a function's identity is its `ir.Symbol` pointer and `ir.Table` is one per lowering, so an incremental lowering needs a builder kept alive per program, which touches most of `internal/irbuild`; it is not planned while that pass only reports builder gaps, and belongs with an on-disk cache of lowered code, which needs the same identity by name. The CLI: `nomi run`, `check` and `test` analyze and lower from scratch (1.4 s at 50k lines); an on-disk cache of each file's interface would serve them. The REPL re-checks every live declaration on each input (below).
- [ ] **Incremental REPL checking.** Each REPL input re-checks and re-lowers every live declaration from source, so an input costs more as the session grows. Types, impls and imports are not versioned the way functions and values are: redeclaring a type drops everything that names it, and a redefined `impl` replaces the old one for earlier definitions too (`cmd/nomi/repl_vm.go`). Both go away when an input can be checked against the session's earlier analysis instead of its source.
- [ ] **Debugger follow-ups.** The debugger plan has landed (feature-status's *Debugger* section). Left: attaching to a running process or a `nomi build` executable (the image keeps the debug info); debugging a program with Go bindings, which runs in a generated wrapper process; and step back in a program with more than one task, which a replay cannot reproduce without recording the scheduler's choices too.
- [ ] **Programs the builder declines.** The checker accepts some programs the IR builder cannot lower, and `nomi run` refuses them before running with a "not supported yet" error at the code the builder stopped at. Every recorded program runs, so each remaining shape is a gap an ordinary program can hit. The known shapes are listed under feature-status's known defects.
- [ ] **The builder's `mobile` flag.** The builder's `lower` still returns whether a value may be read more than once without a copy, and about a hundred call sites pass it on. The VM evaluates each temporary once, so the flag and the `irCopyForce` copies it guards could go. It is a large mechanical change with no behaviour behind it.
- [ ] **FFI follow-ups.**
  - Runtime-typed dispatch (an `import_impls` escape hatch) for values from FFI or deserialization whose impls the analyzer cannot record statically.
  - `host type` field access and Nomi-side construction.
- [ ] **A prebuilt `nomi` still needs Go for Go FFI.** `nomi run`/`test`/`check`/`build` on a Go-FFI project build a wrapper or a nomi-vm that links the compiler's own Go module beside the project's bindings, so they need a Go toolchain. A versioned `nomi` (a release, or `go install ...@version`) requires that module at its own version and Go fetches it; without Go it refuses with a message (`internal/ffirun`, `internal/gotoolchain`). A program importing `std/compiler` needs Go for `nomi build` too, since its nomi-vm variant is not shipped. Homebrew and Scoop packages are not written: they need a tap and a bucket repository.
- [ ] **Standalone WASM programs, what remains.** `nomi build --target js/wasm` and `--target wasip1/wasm` write valid modules, and the wasip1 ones need no file access. A hello world is 11 MB (2.0 MB brotli) and starts in about 130 ms under Node, most of it compiling the module. Browser use is checked by hand in Chromium only: `nomi build --web` pages, a cached wasip1 `nomi-vm` running `.nomic` programs framed on stdin through `@bjorn3/browser_wasi_shim`, and `nomi-wasi.js` loading and running programs in the reactor. The automated tests drive all of these under Node; Firefox and Safari are untried. wasmtime has run a command module; the reactor has not been tried there. GC behaviour is unmeasured. `--web` links a project's Go bindings into `app.wasm` (tested under Node; a bound package that does not build for js/wasm is refused at its `gopkg`), refuses file access where a `files` option served from the worker's `fs` could stand in, and has no `nomi test` counterpart.
- [ ] **Calling JavaScript from Nomi.** A page calls a Nomi program's exported functions (`nomi.js`'s `load` and `call`), but Nomi cannot call the page: no DOM, `fetch` or local storage. The mirror of `export fn` would be a small set of host functions in a `std/web`-like module, or the page passing callbacks to `load`. Nothing is designed.
- [ ] **An npm package for the wasm build** (`cmd/nomi-wasm`, the tour's runtime) with a small JS API: run source, hover, semantic tokens.
- [ ] **Tour hardening, what remains.** The stack-depth limit (`rt/calldepth_js.go`, 1,000 calls) and the run-worker's recovery were measured in Chrome and Node only; Firefox and Safari are unmeasured. And a Go fatal error prints a goroutine trace to the worker's console naming the build machine's paths; `-trimpath` would remove them, and it must go on both `scripts/build-tour-wasm.sh` and `vmhost/tour_bundle_test.go`'s rebuild at once.
- [ ] **Doc-gen, registry and package-manager UX.** `nomi doc`, publishing, distribution polish. Nomi modules ride the Go module proxy.

## Track 2: Irreversible semantics

- [ ] **Language versioning and compatibility.** The mechanism (editions, fixers, a compatibility promise) for when the language stops breaking. Until then it breaks freely, which is correct before a first release.

## Track 3: Architecture to leave room for

- [ ] **A stable serialization format.** The linked-IR image (`ir.EncodeImage`/`DecodeImage`) is the one serialized form today and carries no compatibility promise. Incremental compilation will want front-end artifacts serialized too; design the formats together rather than ad hoc.
- [ ] **WASM Component Model interop** for cross-language imports and exports. WIT interfaces and `wasip2` components are the standard that would replace the wasip1 reactor's generic `nomi_call` ABI, which passes function names and JSON as data because one prebuilt runner serves every program and Go fixes a module's export names when it links it. Go cannot produce components yet. Track it; nothing is designed.

## Track 4: Big but additive

- [ ] **Unified container type/value syntax.** Tuples (`#(Int, String)` ↔ `#(1, "x")`) and anonymous structs (`{a: Int}` ↔ `{a: 1}`) already use one outer syntax for type and value; lists and maps do not (`List<Int>` vs `[1, 2, 3]`). Proposal: also accept `[Int]` and `%{String => Int}` as type forms. Needs its own design.
- [ ] **Field-projection derive** (`derive Getters for T`). For an interface whose functions are pure field projections (`fn hour(value: self) -> Int`), synthesize the trivial impl, which would remove boilerplate like `std/calendar`'s `DateParts`/`TimeParts` impls. `derive` covers `Equatable`, `Hashable`, `Comparable`, `Debug`, `Display`, `ToJson` and `FromJson` today.
- [ ] **Opaque handles for exported functions.** Every argument and result of an `export fn` crosses as JSON, so a value the host passes back unchanged is encoded and decoded on each call. A handle (a value that stays in the VM, referred to by an id) would matter for large values and values with no JSON form. Wait for a program that needs it.
- [ ] **Checked examples in stdlib `///` comments.** The generated reference renders a declaration's `//!` attached tests as runnable editors, and those are the stdlib's examples. A ` ```nomi ` block inside a `///` comment is only highlighted: nothing parses, checks or runs it, so one can go stale unnoticed. Either check those blocks or settle that `//!` is the only example form.

## Track 5: Standard library I/O and services

Where each item lives follows one rule. std holds what Go's standard library can back with no third-party code: `std/fs`, `std/sql`'s vocabulary, later `std/http` over `net/http`. `lib/` holds first-party modules that need third-party Go code or are opinionated layers over std: database drivers (`lib/sql/sqlite`), `lib/sql/sqlkit`, later an HTTP router or framework. Each `lib/` module is its own module with its own `go.mod`, versioned with nomi's commits, tested by nomi's checks, and added by users with `nomi add github.com/nomi-language/nomi/lib/...`.

What a program needs to talk to the world outside the VM. The items are in the agreed order. Items 1, 2 and 6 share one stream type (`Reader`/`Writer`) and one test seam, and are designed together in the I/O design proposal (`docs/design/io.md`, not committed), which also sketches 3, 4, 5 and 7. Every item is backed by Go's standard library, so no program needs a Go toolchain to use it.

- [ ] **2. The file system, the rest.** `std/fs`, `std/path` and `std/fs_testing` exist (whole files with a `WriteMode`, lines and chunks, streams, directories, walks and globs, metadata, symlinks and modes, `io.File` with reads and writes at a position, `fs.within` over `os.Root`, temporary directories, an in-memory sandbox, a conformance suite, the browser's in-memory file system). Missing: `Reader.from_chunks` and `Writer.from_fn`, adapters a program writes; a `Result`-aware `reduce`, which would shorten a fold over `fs.lines`; and a test group line that seals a test's real file calls. Paths use `/` on every system, Windows hosts accepting `\` too; that needs a Windows CI job before a release ships it.
- [ ] **3. Encodings and hashing.** `std/hash` computes SHA-256 (`hash.sha256`, `hash.sha256_hex`); `Seed.from_os` reads OS entropy only to seed `std/random`. Missing: base64, hex and percent encoding of arbitrary bytes, SHA-512, HMAC with a constant-time compare, and secure random bytes. All but the last are pure, so typed literals may use them.
- [ ] **4. Channel `select` with timeouts.** Channels multiplex through one channel of a tagged enum (spec §20, *Multiplexing*), and `select` is listed as a follow-on there. Missing: waiting on several channels and a timer at once, and a receive with a timeout, both on the clock in force so `Clock.Virtual` tests stay instant. Open: which ready arm wins, which Go picks at random.
- [ ] **5. HTTP, then the server.** No networking module exists, and the spec's §24 says so. First a client (`std/http`, `std/url`) whose bodies are item 2's `Reader`s, which honours the context's deadline and works on js/wasm through `fetch`, with a test seam of the same shape as item 2's. Then a server whose requests run as tasks under a supervisor, so `max_running` bounds them and shutdown drains them, plus TCP and TLS.
- [ ] **6. Subprocesses.** Nothing exists. Missing: an immutable `Command` value with no shell, `process.run` and `process.output` to completion, and `process.with_spawned` for streaming over item 2's `Reader` and `Writer`, which kills and reaps the child when its body ends so no process outlives its owner, plus a recording fake (`process_testing`) in `std/sql_testing`'s style. Refused at build time on js/wasm and wasip1. It depends only on item 2, so it could move ahead of item 5.
- [ ] **7. A std `Logger`, then an actor helper.** The spec's §26 example and the tour define a `Logger` interface of their own. Missing: a std `Logger` with levels and fields, text and JSON loggers that write one record per write, and a test recorder; then a helper over item 4's `select` that packages the tour's counter-server pattern (state folded in one supervised task, calls answered on reply channels with a timeout).
